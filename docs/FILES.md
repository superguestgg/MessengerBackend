# Файлы и голосовые сообщения

План отправки файлов и голосовых с заделом под их расшифровку. Общий план — в [ROADMAP.md](ROADMAP.md), правила архитектуры — в [CLAUDE.md](../CLAUDE.md).

## Цель

- В сообщении можно отправить файлы и картинки (до 10 штук) с подписью или без.
- Голосовое — отдельный вид вложения: записывается в браузере, проигрывается в ленте.
- Расшифровка голосовых: в модели и API есть с самого начала, включается позже без переделки API и фронта.
- Агент по MCP видит вложения и расшифровку в `read_messages` / `wait_for_reply`, а сам файл скачивает по REST тем же токеном.

## Решения

### Новый модуль `Messenger.Files`

Файлы — отдельная предметная область, поэтому это модуль `Messenger.Files` с контрактами `Messenger.Files.Contracts`, а не папка в Chats.

- Агрегат `StoredFile`: `Id`, `OwnerId` (кто загрузил), `FileName`, `ContentType`, `Size`, `CreatedAt`, `AttachedAt?`.
- Метаданные — в коллекции `stored_files`, байты — в GridFS-бакете `file_contents` (коллекции `file_contents.files` и `file_contents.chunks`) под тем же `Guid`. Доменное состояние в `metadata` GridFS не храним: GridFS — деталь хранилища.
- Хранилище закрыто интерфейсом `IFileStorage`: GridFS можно заменить на S3-совместимое хранилище без изменений в домене и API.
- `IFilesApi` для других модулей (только примитивы): метаданные своих файлов, «пометить прикреплёнными», открыть поток на чтение.
- Файлы, не прикреплённые к сообщению за 24 часа, удаляет фоновая уборка.

### Почему GridFS

Новой инфраструктуры не нужно: MongoDB уже есть, бэкапы и репликация общие с остальными данными. Голосовое (≈100–150 КБ в минуту) — один-два чанка. Минусы: место в базе дорогое, весь трафик идёт через бэкенд, нет CDN и подписанных ссылок. При лимите в 1 МБ на файл и небольшом числе пользователей это приемлемо. Переход на S3 — когда упрёмся в квоту базы или захотим видео.

### Загрузка отдельным шагом

1. `POST /api/files` (multipart) → `{ fileId, fileName, contentType, size }`.
2. `POST /api/chats/{chatId}/messages` с `fileIds` или `voice: { fileId, durationSeconds }`.

Номер сообщения выдаётся до записи, а `ContiguousMessages` пропускает дыру в нумерации через 5 секунд. Долгая загрузка между выдачей номера и записью сообщения привела бы к тому, что ожидающие перепрыгнут через сообщение. Поэтому сначала файл, потом быстрая отправка.

Прикрепить можно только свой файл. Один и тот же файл можно прикрепить к нескольким сообщениям: доступ к нему всё равно проверяется через сообщение.

### Вложения в Chats

- `Message.Attachments` — список `Attachment { FileId, Kind: File | Image | Voice, FileName, ContentType, Size, DurationSeconds?, Transcript? }`. Метаданные файла копируются в сообщение: файл после загрузки не меняется, а запрос в Files при каждом чтении не нужен.
- Инварианты (`MessageContent`): есть текст или вложения; вложений не больше 10, без повторов; голосовое — одно, без других вложений и без подписи.
- `Kind` определяет домен: `Image` — для `image/png`, `image/jpeg`, `image/gif`, `image/webp`; `Voice` — когда клиент отправил файл как голосовое (тогда тип обязан быть аудио); остальное — `File`.
- Скачивание: `GET /api/chats/{chatId}/messages/{seq}/attachments/{fileId}`. Chats проверяет, что запрашивающий — участник чата и что файл из этого сообщения, затем отдаёт поток через `IFilesApi`. Files про чаты ничего не знает.
- Безопасность: бэкенд раздаёт фронт с того же домена, поэтому загруженный HTML или SVG — хранимый XSS. Картинки и голосовые отдаются `inline`, всё остальное — `Content-Disposition: attachment` и `application/octet-stream`; всегда `X-Content-Type-Options: nosniff`.
- Фронт не может передать заголовок `Authorization` в `<img src>`, поэтому качает вложение через `fetch` в `Blob` и показывает по object URL. При лимите 1 МБ это дёшево.

### Лимиты

| Что | Значение | Где |
|---|---|---|
| Размер файла | 1 МБ | `StoredFile.MaxSize` |
| Вложений в сообщении | 10 | `MessageContent.MaxAttachments` |
| Длительность голосового | 5 минут | `Attachment.MaxVoiceDurationSeconds`; фронт пишет opus 24 кбит/с, это ≈ 0,9 МБ |
| Имя файла | 255 символов | `FileName.MaxLength` |

Больше 1 МБ — 413.

### Задел под расшифровку

- У голосового есть `Transcript { Status: None | Pending | Done | Failed, Text? }`. Пока распознавание выключено, статус `None`; API и фронт уже показывают расшифровку и её состояние.
- Когда включим:
  - порт `ISpeechToText` в `Messenger.Chats/Application`, реализация в `Infrastructure` (Whisper API, Deepgram, Yandex SpeechKit или свой whisper.cpp / faster-whisper в контейнере), выбор — настройкой;
  - голосовое создаётся со статусом `Pending`; после сохранения событие ставит его в фоновую очередь (`BackgroundService` + `Channel`);
  - воркер берёт аудио через `IFilesApi`, вызывает `ISpeechToText`, затем `message.CompleteTranscript(text)` или `FailTranscript()`, сохраняет и будит ожидающих;
  - при старте сообщения в статусе `Pending` подбираются из базы заново — перезапуск ничего не теряет;
  - для `wait` голосовое в статусе `Pending` выглядит как «молодая дыра» (с таймаутом): агент в `wait_for_reply` сразу получает текст, а порядок сообщений не нарушается.
- Расшифровка — данные от человека, как и текст: агенту её нельзя исполнять как инструкции.

## Этапы

1. ✅ **Файлы.** Модуль Files (GridFS, загрузка, уборка неприкреплённых), вложения в сообщениях, скачивание, фронт (прикрепить, картинки, файлы), MCP отдаёт метаданные вложений. Тесты домена.
2. ✅ **Голосовые.** Запись в браузере (`MediaRecorder`), вид `Voice`, длительность, плеер, `Transcript` со статусом `None`.
3. **Расшифровка.** `ISpeechToText` и реализация, фоновый воркер, ожидающие видят голосовое после расшифровки, включение настройкой.

Отложено: отправка файлов через MCP (аргументы инструмента — JSON, файл пришлось бы передавать в base64), превью и сжатие картинок, удаление файлов вместе с сообщениями (удаления сообщений пока нет).
