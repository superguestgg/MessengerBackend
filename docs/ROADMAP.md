# Целевой результат и план

Что мы строим и к чему идём. Текущее устройство кода — в [README.md](../README.md), правила архитектуры — в [CLAUDE.md](../CLAUDE.md).

## Цель

Простой мессенджер с личными и групповыми чатами, ботами и MCP-сервером. Главный сценарий: локальный агент подключается по MCP от имени аккаунта (бота или самого пользователя), пишет в чат и **ждёт ответа** от конкретного человека.

Монорепозиторий `superguestgg/MessengerBackend`:
- бэкенд — в корне (.NET 10, MongoDB);
- фронтенд — `frontend/` (React + TypeScript + Vite). Перенесён из `superguestgg/messenger-frontend`, тот репозиторий больше не используется.

## Аккаунты: люди и боты — одна сущность

Сервер работает с **аккаунтом**, а не отдельно с «пользователем» и «ботом». Тип аккаунта — `User` или `Bot`, у бота есть владелец (`OwnerId`).

- Методы API для чатов и сообщений **одинаковые** для всех. Кто выполняет запрос, определяется по токену.
- В профиле и в сообщениях есть признак `isBot` — фронт показывает значок, агент отличает ответ человека от ответа бота.

| | Человек | Бот |
|---|---|---|
| Создание | `POST /api/account/register` | создаёт человек: `POST /api/bots` |
| Вход | email + пароль → JWT | постоянный токен, выдаётся при создании |
| Токены | выпускает личные токены доступа (для агента) | токен перевыпускает владелец |
| Управление | профиль, пароль | владелец меняет имя, удаляет, отзывает токен |

Ограничения ботов (проверки в домене, а не отдельные методы API):
- бот не может первым написать в личку, пока человек сам не начал диалог или не добавил его в чат;
- бот не создаёт других ботов и не выпускает токены.

### Аутентификация

Один формат для всех клиентов — заголовок `Authorization: Bearer <токен>`:
- **JWT** — для людей во фронтенде, выдаётся при входе, ограниченный срок жизни;
- **токен доступа** — для ботов и личных токенов людей (агент от имени пользователя). Хранится в базе только хешем, у токена есть название и его можно отозвать.

Cookie не используются: нет CSRF и нет проблем с third-party cookies при фронте и бэкенде на разных доменах.

## Чаты и сообщения

Модуль `Messenger.Chats` (чаты и сообщения — два агрегата одного модуля), по правилам из CLAUDE.md:
- `Chat` с типом `Direct` или `Group`, участники `ChatMember { UserId, Role, ... }`, роли `Owner` / `Admin` / `Member`;
- у сообщения **возрастающий номер внутри чата** — на нём строятся подгрузка истории, «всё новее N» и long polling;
- в сообщении хранится только `UserId` автора, имя и аватар подставляются при чтении.

## API (общее для людей и ботов)

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/me` | кто я: аккаунт, тип, профиль |
| `GET` | `/api/chats` | мои чаты |
| `POST` | `/api/chats/direct`, `/api/chats/group` | создать личный (идемпотентно) или групповой чат |
| `POST` | `/api/chats/{id}/members` | добавить участника, в том числе бота |
| `GET` | `/api/chats/{id}/messages?after=N` | история |
| `POST` | `/api/chats/{id}/messages` | отправить сообщение |
| `GET` | `/api/updates?offset=N&timeout=30` | long polling: все новые события аккаунта (отложено до real-time) |
| `GET` | `/api/chats/{id}/messages/wait?from=…&replyTo=…&after=N&timeout=30` | ждать сообщение от конкретного аккаунта в чате, при необходимости — ответ на конкретное сообщение |

Управление ботами и токенами:

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/auth/login` | email + пароль → JWT |
| `POST` | `/api/bots` | создать бота, сразу вернуть его токен |
| `GET` | `/api/bots` | мои боты |
| `POST` | `/api/bots/{id}/token` | перевыпустить токен бота |
| `DELETE` | `/api/bots/{id}` | удалить бота |
| `POST` / `GET` / `DELETE` | `/api/tokens` | личные токены доступа |

## Long polling

- `getUpdates(offset, timeout)` — общий поток событий аккаунта, как у ботов Telegram. Есть новое — ответ сразу, нет — запрос висит до таймаута и возвращает пустой список. **Отложено**: сделаем вместе с real-time для фронта, им нужен один механизм.
- `waitForMessage(chatId, from, replyTo, after, timeout)` — обёртка для сценария «жду ответа от конкретного человека на конкретный вопрос».
- Реализация: сообщение сохраняется в Mongo, ожидающие запросы будятся уведомлением в памяти процесса. Для одного экземпляра сервера этого достаточно; тот же механизм позже питает real-time для фронта (SignalR / WebSocket / SSE).
- Таймаут ожидания (~30 с) должен быть меньше таймаута прокси перед бэкендом (у nginx по умолчанию 60 с).
- Номера сообщений могут становиться видимыми не по порядку (номер выдан, сообщение ещё пишется) и иметь пропуски. Ожидание должно отдавать сообщения только до первой «молодой» дыры, иначе клиент, перешедший на `after=N+2`, навсегда пропустит `N+1`.

### Безопасность ожидания команд агентом

1. **Фильтр по автору на сервере.** `wait` с `from=<id владельца>` возвращает только его сообщения. Подделать автора нельзя: он берётся из токена отправителя, а не из запроса.
2. **Ответ на конкретный вопрос.** Можно ждать сообщение с `replyTo=<seq вопроса>`. Тогда агент не примет случайное или старое сообщение за ответ. Кроме того, `after=N` гарантирует, что старые сообщения не придут повторно.
3. Агенту — токен бота, а не личный: бот видит только свои чаты, утечка токена не даёт доступа к аккаунту. Лучше всего — личный чат «владелец ↔ бот агента».
4. Ограничения сервера: таймаут ожидания не больше 50 с, лимит одновременных ожиданий на аккаунт, rate limiting.
5. HTTPS в продакшене; токен у агента — в переменной окружения, отзывается в любой момент.
6. На стороне агента текст из чата — данные: список разрешённых команд, без исполнения произвольного текста.

## MCP-сервер

- Встроен в тот же ASP.NET-хост по пути `/mcp`, официальный C# MCP SDK, транспорт Streamable HTTP.
- Аутентификация тем же токеном доступа: каким токеном подключился — от имени того аккаунта и действуешь.
- Инструменты — обёртки над теми же handler-ами Mediator: `whoami`, `list_chats`, `open_direct_chat`, `read_messages`, `send_message`, `wait_for_reply`. Как подключить к Claude Code — в README.
- У MCP-клиентов есть таймаут на вызов инструмента (обычно порядка минуты), поэтому `wait_for_reply` ждёт 30–50 с и при отсутствии ответа возвращает «пока ничего, вызови снова». Агент повторяет вызов в цикле.
- CORS для `/mcp` не нужен: к нему подключаются агенты, а не браузер.

## Фронтенд и деплой

Поддерживаются две схемы, выбор — настройкой, код один:

1. **Фронт и бэкенд на разных доменах** (основной план). Бэкенд разрешает домен фронта через CORS, список доменов — в `appsettings.json` (`Cors:AllowedOrigins`), без `*`. Фронт знает адрес API из `VITE_API_URL`. Для разработки в списке `http://localhost:5173`.
2. **Бэкенд раздаёт собранный фронт** (`dist/` → `MessengerWeb/wwwroot`, `UseStaticFiles` + `MapFallbackToFile("index.html")`). Один домен, CORS не нужен. Неизвестные пути под `/api` и `/mcp` возвращают 404, а не `index.html`.

nginx для обеих схем не обязателен.

Сборка в GitHub Actions: один workflow собирает фронт (`npm ci && npm run build` в `frontend/`), при схеме 2 кладёт `frontend/dist` в `MessengerWeb/wwwroot`, затем `dotnet publish`. Изменение API и фронта под него — один коммит и один PR.

## План (MVP)

1. ✅ **Аккаунты и аутентификация** — тип аккаунта `User` / `Bot`, вход по паролю (JWT), токены доступа, создание ботов, `GET /api/me`, CORS.
2. ✅ **Чаты и сообщения** — REST API, личные и групповые чаты, номер сообщения внутри чата.
3. ✅ **Long polling** — ожидание сообщения в чате с фильтрами на сервере (`getUpdates` отложен): по автору (`from`) и по ответу на конкретный вопрос (`replyTo`), плюс `after=N`; ограничения на таймаут и число одновременных ожиданий.
4. ✅ **MCP-сервер** поверх тех же handler-ов: `whoami`, `list_chats`, `open_direct_chat`, `read_messages`, `send_message`, `wait_for_reply`.
5. **Фронтенд** — вход, список чатов, чат, управление ботами и токенами; клиент API генерируется из Swagger.

Каждый шаг — с тестами; интеграционные проверки идут против живого бэкенда и MongoDB в Docker.
